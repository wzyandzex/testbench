# 时间策略（前后端统一）

本文档用于统一前后端时间字段的定义、传输和展示规则，避免时区偏差、排序错误和区间查询异常。

## 1. 统一原则

1. 后端内部统一使用 `UTC`。
2. 接口中的 `time.Time` 统一输出为 RFC3339（例如 `2026-03-04T10:00:00Z`）。
3. 前端展示可以按本地时区格式化，但回传后端时必须是标准时间格式。
4. 涉及排序或筛选时，优先使用原始时间值，不要使用格式化后的字符串比较。

---

## 2. 常见时间字段类型

### 2.1 RFC3339 字符串（推荐）

示例：

```json
{
  "created_at": "2026-03-04T10:00:00Z",
  "updated_at": "2026-03-04T10:05:00Z"
}
```

前端建议：

1. 解析后再显示本地时间。
2. 列表排序按原始值排序，不按格式化文本排序。

### 2.2 Unix 时间戳（秒或毫秒）

少量接口仍会返回整数时间戳。

示例：

```json
{
  "created_at": 1772618400
}
```

前端建议：

1. 明确单位（秒/毫秒）后再转换。
2. 不要混用单位，必要时统一转换成毫秒再处理。

---

## 3. 前端请求入参规范

1. 日期筛选接口如果要求 `YYYY-MM-DD`，严格按该格式提交。
2. 如果接口要求 RFC3339，必须包含时区信息（`Z` 或 `+08:00`）。
3. 不要提交无时区的字符串（如 `2026-03-04 10:00:00`）。

---

## 4. 典型问题与处理

### 4.1 页面时间“慢 8 小时”

原因：把 UTC 时间当本地时间直接渲染。  
处理：先解析为时间对象，再按目标时区展示。

### 4.2 列表排序不稳定

原因：按格式化字符串排序或秒/毫秒混用。  
处理：统一按原始时间值排序，并统一单位。

### 4.3 区间筛选边界不准

原因：开始/结束时间缺少时区或格式不一致。  
处理：在请求层统一格式化后再提交。

---

## 5. 前端联调检查清单（时间）

1. 是否明确每个时间字段的单位与格式。
2. 是否统一处理了时区转换。
3. 是否避免了字符串排序时间。
4. 是否在请求层统一输出时间格式。
